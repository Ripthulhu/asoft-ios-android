# Pixel PowerVR framebuffer fetch

The 2x iOS boot aborted at a framebuffer-fetch pipeline for color attachment 0,
Metal format 550 (`RGB10A8_2P_XR10`). The descriptor enabled all four color
channels without blending on attachment 0. The other two color attachments
disabled writes, and the descriptor included a combined depth/stencil
attachment. [Boot evidence](../device-checks/recovery-20261122/macos-hfs-replay/GPU-BOOT.md)

## Tested Vulkan path

The fixture uses coherent reads from an FP16 working attachment through
`VK_EXT_shader_tile_image`. It performs four overlapping read-modify-write
operations per pixel in a single dynamic rendering pass. Both primitives
in a final draw fail the depth test. The other two color attachments keep
their original values. The host checks every channel of every pixel as
exact FP16 bits. [Vulkan extension](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_shader_tile_image.html)

| Pixel 10 Pro XL test | Process exit | Mismatching pixels |
| --- | ---: | ---: |
| Coherent tile fetch with depth/stencil | 0 | 0 |
| Replace tile read with the original clear value | 1 | 256 |
| Let both depth-rejected primitives pass | 1 | 256 |

The system PowerVR D-Series driver reported color tile reads, accelerated
coherent tile reads and independent blend state. The passing run checked
256 pixels on all three color attachments.

## Build and run

Build the fixture with an installed Android NDK and Python 3. The phone run
used NDK 30.0.14904198 and a 16 KiB-aligned arm64 executable. The build
accepts the NDK's older SPIR-V assembler by checking the temporary
instruction encoding before replacing it with the tile-read opcode.

```sh
python3 build_fixture.py /path/to/android-ndk /path/to/output
adb push /path/to/output/tile_fetch /path/to/output/*.spv /data/local/tmp/
adb shell 'cd /data/local/tmp && chmod 700 tile_fetch && ./tile_fetch feedback.vert.spv feedback.frag.spv'
```

The two negative controls are `negative.frag.spv` in place of
`feedback.frag.spv`, and `negative-depth.vert.spv` in place of
`feedback.vert.spv`. Each should produce 256 mismatches.

## Packed XR round trip

Pass `xr_codec.comp.spv` as the third shader argument to run the packed
mode. The compute shader decodes four repeating RGB10 and A8 code patterns
from an `R32G32_UINT` storage image into the FP16 attachment. The fixture
holds that attachment across three dynamic-rendering instances and stores
it back into the packed image after the last one. The host checks all 256
packed texels, the FP16 values and the two untouched attachments. The
patterns include negative and above-one channels and RGB code 1023,
which the renderer clamps to 1022 when loading the tile.

On the Pixel, the first version that let the image store round the decoded
values differed in 128 FP16 pixels. The packed output bytes masked that
error. Rounding decoded values explicitly to a representable binary16
value before the store brought both checks to zero mismatches. The host
also checked the rounding calculation for all 1,024 RGB codes and 256
alpha codes against a binary16 conversion.

| Packed-mode test on Pixel | FP16 mismatches | Packed mismatches |
| --- | ---: | ---: |
| Explicit half rounding and coherent fetch | 0 | 0 |
| Replace the fetch with a constant | 256 | 256 |
| Make the final draw pass depth | 256 | 256 |

## Renderer integration

The [renderer patch](../../../patches/pixel10-xr/0001-linear-xr-shadow-store.patch)
adds the linear XR store counterpart to the existing shadow load. The
[build run](https://github.com/Ripthulhu/asoft-ios-android/actions/runs/45220112039)
reconstructed the pinned source tree, passed the Rust runtime check and all
three shadow tests, and validated both renderer-generated compute shaders.
Pass those two shaders separately to use them in place of the GLSL fixture.

```sh
./tile_fetch feedback.vert.spv feedback.frag.spv xr-load.spv xr-store.spv
```

| Shader generated by the renderer | SHA-256 |
| --- | --- |
| `xr-load.spv` | `2f3049adc39a03f802657cd97faf1e023e867844d31f2df41312a820ab65aea4` |

On the Pixel the generated shaders produced zero FP16 mismatches and zero
packed mismatches across all 256 texels. Both negative controls produced
256 mismatches in each check. The fixture's own fragment shader exercises
tile fetch, depth/stencil and the two untouched auxiliary attachments.

## Render-pass integration candidate

The [second renderer patch](../../../patches/pixel10-xr/0002-use-xr-tile-shadow.patch)
uses an FP16 attachment for compatible single-sample, single-layer linear
`RGB10A8_2P_XR10` framebuffer fetches. It keeps the FP16 values across
consecutive compatible draws, decodes the packed image on load and packs
the last FP16 values on store. It requires coherent tile-image color reads
and typed storage for both image formats.

Apply patches `0001` and `0002` in order after the CPU-shadow renderer
tree `1b8c0eff2356c3a05cc372b6ea25e74cbdeff8d0`. The physical phone's
existing build still uses the source tree recorded in the
[CPU-shadow patch series](../../../patches/cpu-shadow/README.md).

The [verification workflow](https://github.com/Ripthulhu/asoft-ios-android/actions/runs/45238282949)
reconstructs that source and builds an Android ARM64 smoke test with a
Vulkan 1.3 instance. The public render encoder runs a clear pass with three
draws followed by a separate pass loading the packed result. Each pass checks
256 pixels. The expected red values are 0.5009765625 and 0.501953125.

```sh
# From the extracted Android artifact on the device, in a writable directory.
mkdir -p cache
chmod 700 xr_tile_draw
XDG_CACHE_HOME="$PWD/cache" ./xr_tile_draw xr_tile_draw.air
```

The focused host tests cover the XR shader link and the conversion kernels.
On the Pixel 10 Pro XL with the system PowerVR D-Series DXT-48-1536 MC1
driver, the Vulkan 1.3 smoke executable exited zero. The clear pass and
packed reload each matched all 256 pixels. The runtime reported a split
into three Vulkan rendering instances for the clear pass. This test checks
precision and does not measure the cost of splitting a render pass.

2× iOS 26 boot overlay. The previous boot inputs and its package remained
available for comparison. The first frame and full guest boot require
their own device evidence.
